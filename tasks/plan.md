# План реалізації: netbench — утиліта діагностики мережевих вузьких місць

## Огляд

Утиліта `netbench` — один Go-бінарник: запускає навантаження за сценарієм (iperf3, OSU, GPCNeT, fio),
паралельно збирає метрики хостів і мережі, порівнює з baseline без навантаження і видає
вердикт: вузьке місце — мережа чи CPU/інструмент, і який саме мережевий симптом
(правила: `docs/bottleneck-diagnosis.md`). Поруч — документні результати: таблиця
навантажень, матриця тестів, звіти прогонів на тестовій топології, рекомендації.
Здача — репозиторій з кодом; усі документи лежать у `docs/` у форматі md.

Виконавці: **М** — Марина Огінська, **Н** — Назар Михайлищук, **М+Н** — спільно.

## Архітектурні рішення

- **Усе на Go, один бінарник `netbench`, три підкоманди:**
  - `netbench run <scenario.yaml>` — на контролері: запуск генераторів по SSH, ступеневе
    навантаження, збір, наприкінці автоматично аналіз.
  - `netbench agent` — на кожному хості: збір метрик.
  - `netbench analyze <results/run-id>` — аналіз окремо, на старих результатах.
  - **Тільки Linux.** Утиліта (і контролер, і агент) працює лише на Linux. `make build`
    завжди збирає `GOOS=linux`, тож один і той самий бінарник іде і на контролер, і на хости.
    Розробка: Н — на Linux напряму; М — на macOS: код і `go test` для чистої логіки (аналіз,
    парсери) працюють локально, а запуск утиліти й топології — у Linux VM (OrbStack/Docker Desktop).
- **Аналіз і звіт на Go:** статистика (середнє, p99, кореляція) — `gonum/stat`; звіт —
  `report.md` з PNG-графіками (`gonum/plot`). Markdown читається прямо на GitHub і в diff,
  тому звіти в `docs/results/` видно в репо без запуску. Табличні операції — звичайні цикли
  по структурах, без аналога pandas.
- **Залежності — мінімум:** stdlib (`os/exec`, `encoding/json`, `flag`), `gopkg.in/yaml.v3`,
  `gonum.org/v1/gonum`, `gonum.org/v1/plot`. SSH — системний `ssh`/`scp`
  через `os/exec`, без Go-бібліотеки SSH.
- **Контракт даних — перша задача.** Формат сценарію (YAML) і формат каталогу результатів
  фіксуються до коду. Після цього М (аналіз) і Н (запуск + збір) працюють паралельно:
  аналіз розробляється на fixture-каталогах, не чекаючи живого збору.
- **Каталог прогону = єдиний інтерфейс між модулями:**
  ```
  results/<run-id>/
    scenario.yaml          # копія сценарію
    steps/<step>/tool/<host>.json  # розпарсений вихід генератора (throughput, latency p50/p99)
    steps/<step>/metrics/<host>.jsonl  # семпли: {"ts","host","src","key","value"}
    baseline/metrics/<host>.jsonl      # те саме без навантаження
    verdict.json           # результат аналізу
    report.md              # людський звіт
    charts/*.png           # графіки звіту
  ```
  Точний формат — типи й коментарі в `internal/scenario/results.go`: ім'я кроку `NN-streams-S` (`02-streams-4`),
  лічильники в семплах — швидкість за секунду, а не сирі значення, метрики Docker-хоста й маршрутизаторів — хост `_infra`,
  `lat_p99_ms` у результаті інструмента — `null`, якщо інструмент його не міряє (iperf3).
- **Віддалений запуск через SSH.** `netbench run` на контролері запускає по SSH той самий
  бінарник у режимі `netbench agent` на кожному хості (збір метрик) і генератори навантаження,
  потім забирає файли через scp. Окремого протоколу агента немає — додати, якщо SSH стане
  обмеженням.
- **Збирачі читають `/proc` і `/sys` напряму** (`/proc/stat`, `/proc/net/snmp` і `netstat`, `softnet_stat`,
  `/sys/class/net/*/statistics`, cgroup `cpu.stat`) замість обгорток `mpstat`/`nstat`/`ip -s link`; лише ping-проба —
  зовнішня команда. Опитування раз на секунду, `netbench agent` — той самий бінарник. `ss -ti` і `ethtool -S` — у беклозі.
- **Правила діагностики — таблиця в коді** (`internal/analyze`), один рядок = одне правило з
  `docs/bottleneck-diagnosis.md`, пороги в одному місці (тюнінг на вимірюваннях).
- **Фіксована тестова топологія = «надана мережа».** Окремої мережі немає; топологію
  задаємо самі й розгортаємо в контейнерах через **containerlab** (Linux; на macOS — у Linux VM):
  ```
        spine1        spine2          FRR-маршрутизатори, BGP, ECMP через обидва spine
         │   ╲      ╱   │
         │     ╲  ╱     │             кожен leaf–spine лінк — окремий veth:
         │     ╱  ╲     │             на ньому tc netem/tbf, його можна вимкнути (відмова)
        leaf1        leaf2
       ╱  │  ╲      ╱  │  ╲
     h1  h2  h3   h4  h5  h6          хости: Linux-контейнери з генераторами і агентом
  ```
  - host–leaf лінки 1 Gbit, leaf–spine — 1 Gbit кожен (`tc tbf`) → oversubscription 3:2 на leaf.
  - Шляхи «в межах leaf» (h1↔h2) і «через spine» (h1↔h4) — для локалізації рівня.
  - Incast: h2..h6 → h1. Балансування: багато потоків h1→h4 через обидва spine.
  - Відмова: `ip link set down` на лінку leaf1–spine1 або зупинка spine-контейнера.
  - Профілі мережі (чиста / oversubscribed / з втратами) — окремі файли параметрів `tc`,
    а не окремі топології.
  - Топологія фіксована в `testbed/topology.clab.yml` і не змінюється після Checkpoint 1,
    щоб результати були порівнянні.
- **MVAPICH у першій версії, транспорт — TCP/Ethernet.** OSU Micro-Benchmarks запускаються
  через MVAPICH, зібраний з libfabric (провайдер `tcp`), бо RDMA-заліза в контейнерах немає.
  Результати MVAPICH поверх TCP не відображають його RDMA-продуктивність — це записується
  в обмеження. RDMA (Soft-RoCE) — у беклозі (`tasks/todo.md`, розділ «Беклог»).
- **«Гіпервізор» = машина, на якій працює Docker.** Усі хости *і маршрутизатори* ділять
  одні CPU. Тому збираємо ще (а) загальне навантаження CPU Docker-хоста і (б) CPU кожного
  контейнера-маршрутизатора (`docker stats` / cgroup). Якщо spine-контейнер упирається в
  CPU, то «мережева» проблема насправді CPU-шна, і звіт має це показати.

## Пайплайн утиліти і вивід результатів

### `netbench run scenario.yaml`

```
1. Сценарій      читає YAML, перевіряє поля
2. Перевірка     SSH до всіх хостів, наявність iperf3/mpstat/..., копіює bin/netbench на хости
3. Baseline      агенти збирають метрики N секунд без навантаження
                 + один короткий прогін генератора з мінімальним навантаженням (1 потік)
4. Кроки         для кожного кроку (1, 2, 4, 8 потоків; 2, 4 вузли):
                   агенти старт → прогрів 5 с → генератор → агенти стоп
                   (у заданий момент — внесення несправності, якщо сценарій її задає)
5. Збір          scp: вивід генераторів + метрики хостів + CPU маршрутизаторів → results/<run-id>/
6. Аналіз        на кожен крок: середнє і p99 метрик, дельти відносно baseline
                 → правила з bottleneck-diagnosis.md → вердикт на кожен крок
                 → крок, з якого почалося вузьке місце (продуктивність перестає рости)
7. Вивід         термінал + verdict.json + звіт
```

Кроки 6–7 — те саме, що `netbench analyze <results/run-id>`. Синхронізація годинників не
потрібна: контейнери топології ділять годинник ядра.

### Вивід: три рівні

**1. Термінал** — прогрес під час прогону, наприкінці таблиця кроків і висновок:

```
iperf3-basic  h1 → h4 (через spine)                      run 2026-11-25_1432

крок   потоки  Gbit/s  RTT p99  retrans/s  CPU max  вердикт
base   1       0.94    0.3 ms   0          18 %     —
1      1       0.94    0.4 ms   0          21 %     немає вузького місця
2      4       0.95    3.1 ms   120        34 %     мережа: перевантаження
3      8       0.91    7.8 ms   410        41 %     мережа: перевантаження

ВИСНОВОК  мережа — вузьке місце з кроку 2 (4 потоки)
          симптом: перевантаження каналу (retrans ↑, RTT холостої проби ↑ ×10, CPU < 50 %)
          рівень: spine (пара в межах leaf h1→h2 без деградації)
УВАГА     spine1: CPU контейнера 92 % — вердикт може бути CPU-шним, а не мережевим

звіт: results/2026-11-25_1432/report.md
```

**2. `verdict.json`** — те саме як дані: для тестів і порівняння прогонів.

**3. Звіт `report.md` + `charts/*.png`**, розділи по порядку:
1. **Відповідь:** чи мережа — вузьке місце, симптом, з якого кроку, рівень (access / spine), впевненість.
2. **Докази:** таблиця всіх правил зі статусом *спрацювало / не спрацювало / не перевірено*
   і числами (значення vs baseline). «Не перевірено» обов'язкове — щоб відсутні дані не
   виглядали як відсутність проблеми.
3. **Продуктивність по кроках** — графік з позначеною точкою, де вона перестала рости.
4. **Метрики в часі** (RTT, retrans, CPU) — вертикальні лінії на межах кроків і моментах несправностей.
5. **Інфраструктура** — CPU маршрутизаторів і Docker-хоста; попередження, якщо щось упиралось у CPU.
6. **Дані** — шляхи до сирих файлів у `results/`.

Змішані навантаження (T16) додають таблицю «окремо vs разом»: деградація кожного
навантаження у % відносно його ізольованого прогону.

**Принцип:** кожен вердикт показує числа, на яких він заснований, і порівняння з baseline.

## Граф залежностей

```
T1 контракт даних (YAML + results/)
 ├── T2 CLI-скелет + testbed ──┐
 │                              ├── T3 iperf3 runner (Н) ──┐
 │                              ├── T4 збір метрик (Н) ────┤
 └── T5 аналіз на fixture (М) ──────────────────────────────┴── T6 end-to-end iperf3
                                                                   │
            ┌──────────────────────────┬───────────────────────────┤
     T7–T10 правила діагностики   T11 ступеневе навантаження   T13 OSU, T14 GPCNeT (М)
            (внесення несправностей)   T12 fio/incast (Н)          T15 відмови (Н)
            └──────────────┬───────────┴───────────────────────────┘
                     T16 змішані навантаження, T17 leaf vs spine
                           │
                     T18 калібрування на фінальній топології → T19 звіти → T20 рекомендації
Документи (паралельно з кодом): D1 таблиця навантажень (М), D2 матриця тестів (М+Н), D3 документація утиліти
```

## Фази

### Фаза 0 — Фундамент
T1 (М+Н), T2 (Н), D1 стартує (М).

### Фаза 1 — Наскрізний скелет (iperf3, одна пара хостів)
T3, T4 (Н) ‖ T5 (М) → T6 (М+Н). Після фази утиліта повністю працює на одному сценарії.

**Checkpoint 1:** `bin/netbench run scenarios/iperf3-basic.yaml` на testbed дає `verdict.json`
і `report.md`; з netem-втратами вердикт «мережа», без — «немає вузького місця». Рев'ю обома.

### Фаза 2 — Правила діагностики (кожне правило — вертикальний зріз: несправність → виявлення)
T7–T10 (М пише правила, Н — сценарій внесення несправності на testbed). Паралельно D2.

**Checkpoint 2:** усі 8 правил з `bottleneck-diagnosis.md` мають тест на fixture і
відтворювальний сценарій на testbed.

### Фаза 3 — Навантаження й сценарії матриці
T11, T12, T15 (Н) ‖ T13, T14 (М). Кожне — новий генератор + сценарій YAML + вердикт у звіті.

**Checkpoint 3:** кожен рядок матриці тестів D2 має YAML-сценарій, що проходить на testbed.

### Фаза 4 — Взаємний вплив
T16, T17 (М+Н).

**Checkpoint 4:** змішаний сценарій на testbed дає звіт із деградацією кожного навантаження
відносно його ізольованого запуску. Утиліта заморожується для польових тестів; D3 готова.

### Фаза 5 — Повні прогони на фіксованій топології й висновки
T18 → T19 → T20 (М+Н).

**Checkpoint 5 (фінал):** усі пункти Deliverables з README закриті.

## Ризики і пом'якшення

| Ризик | Вплив | Пом'якшення |
|---|---|---|
| Хости й маршрутизатори ділять одні CPU ноутбука, тож «мережа» і «CPU» — це те саме залізо | Високий | Збирати CPU Docker-хоста і кожного маршрутизатора; обмежити `tc tbf` швидкості лінків нижче за те, що тягне CPU; у звіті позначати вердикт як «непрямий» |
| Різні середовища: М на macOS (Linux VM), Н на Linux | Середній | `testbed/README.md` описує обидва варіанти; T6 відтворюється обома на Checkpoint 1 |
| MVAPICH не збирається з libfabric `tcp` у контейнері | Середній | Почати T13 зі збірки образу; якщо за розумний час не вдається — OSU через MPICH (MVAPICH на ньому базується), MVAPICH лишити в беклозі разом із RDMA |
| GPCNeT складно зібрати в контейнері | Середній | Якщо не збирається, задокументувати й замінити сценарієм «фоновий iperf3 + OSU latency» як моделлю congestion impact |
| Обоє вчите Go під час проєкту | Середній | Перед T1 — Tour of Go; фаза 1 навмисно мала (один сценарій), щоб на ній освоїтися; рев'ю коду одне одного на кожному checkpoint |
| Пороги правил залежать від швидкості машини | Середній | Пороги відносні до baseline, а не абсолютні; фінальне калібрування в T18 |
| `ethtool -S` / cgroup недоступні у VM | Низький | Збирач пропускає недоступне джерело, аналіз позначає правило як «не перевірено» |

## Відкриті питання

Немає. Вирішено: мова — Go, один бінарник (запуск, збір, аналіз, звіт у md з PNG); мережа — власна
фіксована топологія (вище); утиліта тільки під Linux; v1 — MVAPICH поверх TCP/Ethernet, RDMA у беклозі; «гіпервізор» — це
Docker-хост; здача — утиліта в репозиторії.
